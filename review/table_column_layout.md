# 使用记录表格列宽分析与实现

更新：2026-10-09。状态：默认百分比、手动拖动和四列比例保存均已实施并验证；当前运行版已更新和重启。

## 当前默认比例：32% / 26% / 28% / 14%

针对用户反馈的正常窗口下“前两列过宽、后两列过窄”，建议四列统一采用软件 32%、进程 26%、使用时长 28%、占比 14%，均占表格可用内容宽度，合计 100%。这是一组兼顾正常与窄窗口的默认比例，并非统计意义上的唯一最优解。

本次通过只读连接读取当前数据库，按现有合并规则得到 349 项、约 1,159.0 小时，最新记录截至北京时间 2026-10-09。实际字体测量显示，最长时长加两侧留白需 133.3 DIP，当前最长占比需 59.3 DIP，单个软件筛选可能出现的 `100.0%` 需 68.1 DIP。

最窄窗口附近，扣除应用边距、边框与滚动条后，表格可用宽度约 500 DIP。故时长约需 27%，占比约需 14%；取时长 28% 留出少量余量。剩余 58% 分给名称，软件因图标、中文名称及常用项的内容宽度多分一点，取 32% 与 26%。

| 表格可用宽度（DIP） | 软件 32% | 进程 26% | 时长 28% | 占比 14% |
| ---: | ---: | ---: | ---: | ---: |
| 500 | 160 | 130 | 140 | 70 |
| 750 | 240 | 195 | 210 | 105 |
| 1000 | 320 | 260 | 280 | 140 |

以真实 WPF 控件在隐藏布局中比较了四组比例，窗口内容区宽度覆盖 580、600、800、1200 DIP。其中 580 是为窗口边框占用预留空间的保守检查，其表格实际视口为 504.7 DIP：

- 35/30/25/10：窄窗口下最长时长及占比均不足。
- 34/28/26/12：最窄检查下最长时长及占比不足。
- 33/27/27/13：最长时长足够，但 `100.0%` 在最窄检查下不足。
- **32/26/28/14：所有检查宽度下，当前最长时长和 `100.0%` 均有足够空间。**

宽窗口下四列同时增宽，避免前两列独占新增空间；窄窗口下软件和进程名继续用省略号并提供悬停全称。若未来累计小时位数显著增加，需重新检查最窄窗口或采用更短时长格式。

## 实施与运行验证

- 默认四列采用 WPF Star 布局，权重为 `32* / 26* / 28* / 14*`，随可用视口宽度同步伸缩。
- 恢复四列的手动调节。表头分隔线两侧各有 8 DIP 拖动区域，光标为左右调整；拖动只改变相邻两列，其余两列保持不动。列最小宽度约束防止被拖到不可读；取消拖动恢复原比例并且不保存。
- 拖动结束后转回四列 Star 权重，并把归一化的四列比例保存到本地数据库 `usage_column_ratios`。重新打开时恢复；缺失或无效设置保留默认值。旧的像素宽度设置不再恢复。

## 上一版的数据与问题

本机可读取的 `SoftTrace/softtrace.db` 含 68,771 条活动区间，覆盖北京时间 2025-06-24 至 2026-10-05；按应用现有汇总与名称合并规则得到 344 项、约 1,119.9 小时。这份数据略早于截图中的 349 项、1,158 小时 36 分钟，因此只用于确定合理默认分配。运行时使用当前筛选结果测量，不将该样本数或时长写死。

原布局的软件列为 `5*`、最小宽度 240；进程和时长为固定宽度，占比吸收剩余空间。已有设置还保存了约 `554.3 / 266.7 / 176.7 / 204.3` 的像素列宽，恢复时将前三列固定，因此缩窗后容易横向溢出。软件名采用横向 StackPanel，也无法正确约束文本并生成省略号。

## 上一版的分配规则（已替换）

1. 先测量当前日期与设备筛选结果中**全部记录**的时长和占比，连同表头及留白确定这两列宽度。当前样本时长列为 138，占比列为 64；日期、设备或累计小时位数变化时会重新测量。
2. 将剩余视口宽度按软件∶进程 = 1.1∶1 分配。软件列最小宽度为 140，进程列为 100；WPF Star 布局随窗口连续调整，无需离散断点。
3. 软件名改用有宽度约束的 Grid，软件名和进程名均为单行省略，悬停可读完整名称。
4. 前两列允许手动拖动，保存相对比例而非固定像素，比例限于 0.5∶1 至 2∶1。旧的像素宽度设置不再恢复；时长和占比按内容保留宽度。
5. 换页不会重新按当前页测量，避免列宽跳动。若外部强制将表格缩到四列必要最小宽度以下，保留横向滚动以避免丢失数值；应用正常最小窗口宽度下没有溢出。
